# CLAUDE.md

ElevateAI: an AI-assisted career platform MVP (resume evaluation, profile-to-job gap visualizer, job matching, job portal, dashboards). Product scope is in `ElevateAI MVP Project Proposal.md`; decisions, data model and phased build plan are in `IMPLEMENTATION_PLAN.md`. Read the plan before adding a feature.

## Layout

Bun-workspaces monorepo (`client`, `server`). Note: `IMPLEMENTATION_PLAN.md` describes a future `apps/*` + `packages/shared` layout; the repo currently uses `client/` and `server/`.

- `client/` (`@elevateai/client`): React 19 + Vite 8 + Tailwind 4 + TypeScript. Linted with oxlint. shadcn/ui (radix, nova preset; add components with `bunx --bun shadcn@latest add <name>` from `client/`) and react-router (`BrowserRouter` in `main.tsx`, routes in `App.tsx`, pages in `src/pages/`). `components/theme-provider.tsx` handles light/dark/system (class on `<html>`, `theme` in localStorage, pre-paint script in `index.html`); `components/navbar.tsx` has the nav links (placeholders), theme toggle and Log in / Sign up links. Sign-up is wired: `src/features/auth/` (`auth.schema.ts` zod mirror of the server, `auth.api.ts` axios calls, `auth.store.ts` zustand user, `use-register.ts` TanStack mutation), `lib/api.ts` (axios instance + `getApiError`), react-hook-form + zodResolver on `/register`, Sonner toasts (`<Toaster />` in `App.tsx`). The user is restored from the session cookie on startup: `useSession()` (in `App.tsx`) calls `GET /api/me` via TanStack Query (key `SESSION_KEY`) and syncs the zustand store, whose `status` is `loading | authenticated | anonymous` (the navbar shows a placeholder while loading; route guards should wait for it). A 401 on any protected request clears the user (`lib/api.ts` interceptor). `/login` is wired the same way (`loginSchema`, `loginRequest`, `use-login.ts`; a 401 is one generic toast and clears the password). `/login` and `/register` redirect home when already signed in. Matching UI (feature folders `catalog`, `profile`, `jobs`, `matching`, `applications`): `/resume` (candidate resume builder with version history and restore; `?from=<version id>` starts an edit from a copy of an older version, held in the form until Save; roles and education have move up/down buttons), `/resume/preview` (formatted resume of the current or any older version via `?version=<id>`, with a PDF download and Edit; feature folder `features/resume`: `buildResumeModel` in `resume-model.ts` is a pure builder that both the on-screen `ResumeSheet` and the PDF render, so they cannot drift; the PDF is built in the browser with `@react-pdf/renderer`, lazy-loaded from `resume-pdf.tsx`, A4, Helvetica only, so the preview warns about characters outside Latin; job preferences are never part of it), `/jobs` and `/jobs/:id` (public; the job page shows the candidate's live match card with a Chart.js radar and an Apply button), `/applications` (candidate), `/employer/jobs`, `/employer/jobs/new`, `/employer/jobs/:id/edit`, `/employer/jobs/:id/applicants` (employer). `components/require-role.tsx` guards role pages; `features/catalog/catalog-picker.tsx` is the shared autocomplete. Query keys `['profile']`, `['jobs']`, `['matching']`, `['applications']` are prefixes that mutations invalidate together.
- `server/` (`@elevateai/server`): Express 5 + TypeScript on Bun, Prisma 7 (`@prisma/adapter-pg`) + PostgreSQL with pgvector, Zod 4, helmet, cors.
  - Feature modules with MVC: `src/modules/<name>/` holds `<name>.routes.ts` (paths + middleware only), `<name>.controller.ts` (HTTP in/out only, no business logic), `<name>.service.ts` (business logic + Prisma, no `req`/`res`) and `<name>.schema.ts` (Zod input schemas) when the module takes input. The Prisma schema is the Model layer; there is no view/serializer layer. Create only the files a module needs. Flow: routes -> controller -> service -> Prisma.
  - `src/index.ts`: startup and graceful shutdown. `src/app.ts`: `createApp()` (helmet, cors, auth handler, json, `/api` router, error handlers). `src/routes.ts`: mounts module routers under `/api`; register new modules here.
  - `src/config/env.ts`: Zod-validated `process.env`; exits on invalid config. Import `env` from here, never read `process.env` elsewhere. `src/config/db.ts`: single `prisma` client plus `connectDb` / `isDbConnected` / `disconnectDb`.
  - `src/middleware/errors.ts`: shared `notFound`, `errorHandler`, `HttpError(status, message)`. Error responses are `{ error: { message } }`; 5xx messages are masked.
  - `modules/auth`: `auth.config.ts` is the Better Auth instance (email/password, Prisma adapter, DB-backed rate limits); `role` is an extra user field, sign-up must send `candidate` or `employer` (enforced in `hooks.before`, for every caller) and `/update-user` cannot change it. `auth.routes.ts` serves `/api/auth/*` and is mounted before `express.json()`; the public entry points are `POST /api/auth/register` and `POST /api/auth/login` (Zod `auth.schema.ts`, `registerUser` / `loginUser` in the service, both set the session cookie; login gives one generic 401 for wrong email or password; 5/min IP limit each via `express-rate-limit` (production only), because Better Auth's limiter skips server-side calls). Better Auth's raw `/sign-up/email` and `/sign-in/email` are blocked with 404; sign-out and session stay on Better Auth (`POST /api/auth/sign-out`). `auth.routes.ts` also overwrites the `x-client-ip` header with `req.ip` before the Better Auth handler (and `auth.config.ts` reads it via `advanced.ipAddress.ipAddressHeaders`), otherwise Better Auth rate-limits all clients in one shared bucket; set Express `trust proxy` if deployed behind a proxy. Shared helpers: `middleware/validate.ts` (`validate(schema)` -> 400 with `details`) and `HttpError(status, message, details?)`. `auth.middleware.ts` has `requireAuth` (sets `req.auth`) and `requireRole(...roles)`. `auth.service.ts` has `ensureAdmin`.
  - Matching (design in `IMPLEMENTATION_PLAN.md` section 1a). The score is a pure function: `modules/matching/matching.engine.ts` (`matchEngine`, `checkEligibility`) with weights in `matching.config.ts` (`ENGINE_V1`: skills 35, experience 20, domain 15, education 10, leadership 10, certifications 10; unspecified dimensions are skipped and weights renormalise). No DB, clock, randomness or network in it; arithmetic is integer basis points. V1 was revised once before launch to add education; now that applications store their score and engine version, a change to a weight or rule needs a new engine version, never an edit to V1. Only fields the engine reads affect a score: summary, role company/dates/description and education field/institution/dates are display-only (shown to employers, part of the content hash, never scored). `matching.service.ts` has `scoreMatch` (the one place a profile and a job become a score, used by gap, recommendations and apply), `getGap` (`GET /api/jobs/:id/gap`) and `recommendJobs` (`GET /api/jobs/recommended`). Mount `matchingRouter` before `jobsRouter` in `routes.ts` (its `/jobs/recommended` must beat `/jobs/:id`).
  - `modules/catalog`: curated `CatalogTerm`/`CatalogAlias` (kind `skill|certification|domain`, stable ids like `skill:react`); `GET /api/catalog?kind=&q=`; `seedCatalog` is an idempotent upsert (`bun run db:seed-catalog`; the Playwright server command runs it). `termNamesFor` and `assertApprovedTerms` are the shared helpers; every id stored in a profile or job must be an approved term. `catalog.normalize.ts` makes alias keys (so `React.js` = `reactjs`).
  - `modules/candidate-profile`: `GET/PUT /api/candidate/profile`, `GET /api/candidate/profile/versions`, `POST .../versions/:id/restore` (candidate only). Content is canonicalised and sha256-hashed (`canonicalizeProfile`, `lib/content-hash.ts`); saving identical content reuses a `ProfileVersion`, restore only repoints `currentVersionId`. Roles and education keep the order the candidate arranged (it is what the resume prints), so their order is part of the hash and rearranging them makes a new version with an unchanged score; skills, certifications, other skills, locations and work modes are still sorted and deduplicated. Versions are immutable: never update one in place. Contact details (phone, contact email, city/country, LinkedIn/GitHub/website/other links) are deliberately NOT part of a version: they live in `CandidateProfile.contact` (JSON), are saved by the same `PUT` (as an optional `contact` object; omitting it keeps what is stored), never enter the content hash or the score, and are not touched by restore. Links must be http(s) (`contactSchema`); `parseStoredContact` reads them back and returns empty if stored data no longer validates. Employers see the candidate's current contact in the applicants response only for their own jobs' applicants. Stored content is JSON, so new fields need no migration: read it through `parseStoredProfile` / `parseStoredJob` (they re-apply schema defaults to older versions) instead of casting.
  - `modules/jobs`: public `GET /api/jobs` (active only, filters, cursor) and `GET /api/jobs/:id`; employer `/api/employer/jobs` CRUD plus `publish|unpublish|close` (draft <-> active, active -> closed; other moves 409). Same immutable-version scheme (`JobVersion`); publishing or editing an active job needs at least one scored requirement.
  - `modules/applications`: `POST /api/jobs/:id/apply` freezes the profile version, job version, score, breakdown and engine version; `GET /api/candidate/applications`; `GET /api/employer/jobs/:id/applicants` (ranked by score); `PATCH /api/applications/:id/status` (forward-only: applied -> under_review|rejected, under_review -> rejected|hired).
  - `modules/user`: `GET /api/me`. `modules/health`: `GET /api/health`. `modules/home`: `GET /` at the server root (outside `/api`, mounted in `app.ts`).
  - `scripts/seed-admin.ts`: thin wrapper around `ensureAdmin` using `ADMIN_EMAIL` / `ADMIN_PASSWORD`.
  - `prisma/schema.prisma`: Better Auth models (User, Session, Account, Verification, RateLimit) written by hand because the Better Auth CLI needs a native build; more models are added per phase. Embedding columns use `Unsupported("vector(1536)")` and raw SQL.
  - Prisma client is generated to `server/generated/prisma` (gitignored); import from `../../generated/prisma/client` (see `src/config/db.ts`).
- `docker-compose.yml`: `pgvector/pgvector:pg17` on host port **5433** (user/password/db: `postgres`/`postgres`/`elevateai`).

## Commands (run from repo root)

```
bun install
docker compose up -d db          # start Postgres + pgvector
bun run dev                      # client + server together
bun run dev:client | dev:server
bun run build                    # client only (tsc -b && vite build)
bun run typecheck                # server only (tsc --noEmit)
cd server && bun run db:generate # prisma generate (required after install / schema change)
cd server && bun run db:migrate  # prisma migrate dev
cd server && bun run db:deploy   # prisma migrate deploy
cd server && bun run db:seed-admin # create the admin user from ADMIN_EMAIL / ADMIN_PASSWORD
cd server && bun run db:seed-catalog # seed skills/certifications/domains (idempotent)
cd server && bun test            # unit tests (matching engine, hashing, canonicalisation)
cd client && bun test            # unit tests (resume model); test files are excluded from tsc -b
cd client && bun run lint        # oxlint
bun run test:e2e:install         # one-time: download Playwright Chromium
bun run test:e2e                 # Playwright (boots its own server + client, creates/migrates elevateai_test)
bun run test:db:setup | test:db:reset  # create+migrate / truncate the e2e database
```

Playwright (e2e) is set up in `playwright.config.ts` with specs in `e2e/` (auth, catalog, profile, jobs, matching, applications; helpers in `e2e/support/`). The e2e server command also seeds the catalog. It runs against a separate database `elevateai_test` (same Docker container; override with `TEST_DATABASE_URL`, see `server/.env.test.example`) on its own ports: server 4100, client 5174 (the Vite proxy target comes from `API_PROXY_TARGET`). `server/scripts/test-db.ts` refuses any database not named `*_test`; `reset` also removes the seeded e2e admin (`admin@e2e.test`), which the server re-seeds on its next start. Workers are 1 (shared DB). Rate limiting (Better Auth and the 5/min `express-rate-limit` on `/register` and `/login`) is enforced only when `NODE_ENV=production` (`env.NODE_ENV`, default `development`), so dev and e2e are unthrottled.

Writing e2e tests: do NOT write, update or run e2e tests on your own, even when a feature or page is added or changed. The user asks for them when a feature is complete. When asked, delegate to the `e2e-test-writer` agent (`.claude/agents/e2e-test-writer.md`) instead of writing specs inline. Give it the feature/flow and the behaviours to cover (including failure cases); it reads the code, writes specs and helpers in `e2e/` (shared helpers in `e2e/support/`), runs them against the isolated test stack and reports results. Do not run e2e tests against the dev servers or database.

## Environment

Copy `server/.env.example` to `server/.env`. Required: `DATABASE_URL` (matches the docker-compose port 5433), `BETTER_AUTH_SECRET` (min 32 chars). Optional: `ADMIN_EMAIL`, `ADMIN_PASSWORD` (min 12 chars); when both are set the server seeds the admin on startup (idempotent). `NODE_ENV` (`development` default; rate limiting and secure cookies only apply in `production`, so set it in deploys). Defaults: `PORT=4000`, `CLIENT_ORIGIN=http://localhost:5173`, `BETTER_AUTH_URL=http://localhost:4000`. Never commit real secrets; `.env*` is gitignored except `.env.example`.

## Conventions

- Server is ESM TypeScript run directly by Bun; no build step. Imports are extensionless relative paths.
- Style: no semicolons, single quotes, 2-space indent, trailing commas.
- Validate all external input with Zod (schemas in `<name>.schema.ts`); throw `HttpError` for expected failures.
- Migrations: the first one enables pgvector (`CREATE EXTENSION IF NOT EXISTS vector`). Vector indexes (HNSW, cosine) go in hand-edited migration SQL.
- Auth: Better Auth with roles `candidate | employer | admin`; guard routes with `requireAuth` / `requireRole`. Email verification and password reset are not built yet.
- Planned stack (not yet built): BullMQ + Redis workers, Socket.IO, Vercel AI SDK for LLM calls. Keep to these when implementing those phases.
