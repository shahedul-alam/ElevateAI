# CLAUDE.md

ElevateAI: an AI-assisted career platform MVP (resume evaluation, profile-to-job gap visualizer, job matching, job portal, dashboards). Product scope is in `ElevateAI MVP Project Proposal.md`; decisions, data model and phased build plan are in `IMPLEMENTATION_PLAN.md`. Read the plan before adding a feature.

## Layout

Bun-workspaces monorepo (`client`, `server`). Note: `IMPLEMENTATION_PLAN.md` describes a future `apps/*` + `packages/shared` layout; the repo currently uses `client/` and `server/`.

- `client/` (`@elevateai/client`): React 19 + Vite 8 + Tailwind 4 + TypeScript. Linted with oxlint. shadcn/ui (radix, nova preset; add components with `bunx --bun shadcn@latest add <name>` from `client/`) and react-router (`BrowserRouter` in `main.tsx`, routes in `App.tsx`, pages in `src/pages/`). `components/theme-provider.tsx` handles light/dark/system (class on `<html>`, `theme` in localStorage, pre-paint script in `index.html`); `components/navbar.tsx` has the nav links (placeholders), theme toggle and Log in / Sign up links. Sign-up is wired: `src/features/auth/` (`auth.schema.ts` zod mirror of the server, `auth.api.ts` axios calls, `auth.store.ts` zustand user, `use-register.ts` TanStack mutation), `lib/api.ts` (axios instance + `getApiError`), react-hook-form + zodResolver on `/register`, Sonner toasts (`<Toaster />` in `App.tsx`). The user is restored from the session cookie on startup: `useSession()` (in `App.tsx`) calls `GET /api/me` via TanStack Query (key `SESSION_KEY`) and syncs the zustand store, whose `status` is `loading | authenticated | anonymous` (the navbar shows a placeholder while loading; route guards should wait for it). A 401 on any protected request clears the user (`lib/api.ts` interceptor). `useResetCacheOnUserChange()` (`features/auth`, called in `App.tsx`) removes every cached query except the session when the signed-in user id changes (sign-out, another login, expired session), so one user's data (their company, profile, applications) is never served to the next user of the tab; per-user query keys also include the user id (`useMyCompany`). Owner-only UI checks the viewer's role and ownership, never cached data alone. Sign-out (`navbar.tsx`) clears local state only after the sign-out request settles, otherwise the `/me` refetch from the navigation can find the old session and sign the user back in. `/login` is wired the same way (`loginSchema`, `loginRequest`, `use-login.ts`; a 401 is one generic toast and clears the password). `/login` and `/register` redirect home when already signed in. Matching UI (feature folders `catalog`, `profile`, `jobs`, `matching`, `applications`): `/resume` (candidate resume builder with version history and restore; `?from=<version id>` starts an edit from a copy of an older version, held in the form until Save; roles and education have move up/down buttons), `/resume/preview` (formatted resume of the current or any older version via `?version=<id>`, with a PDF download and Edit; feature folder `features/resume`: `buildResumeModel` in `resume-model.ts` is a pure builder that both the on-screen `ResumeSheet` and the PDF render, so they cannot drift; the PDF is built in the browser with `@react-pdf/renderer`, lazy-loaded from `resume-pdf.tsx`, A4, Helvetica only, so the preview warns about characters outside Latin; job preferences are never part of it), `/jobs` and `/jobs/:id` (public; the job page shows the candidate's live match card with a Chart.js radar and an Apply button), `/applications` (candidate), `/employer/jobs` (employer list: search by title, All/Draft/Active/Closed status buttons with counts, sort; the search text is local state mirrored to `?q=&status=&sort=` and changes merge against the live `window.location`, because router updates are transitions and a URL-controlled input drops characters; clicking a card opens its preview, there are no View/Preview buttons; Close asks via `ConfirmDialog`), `/employer/jobs/new`, `/employer/jobs/:id/edit`, `/employer/jobs/:id/applicants` (employer; the job form has Edit and Preview tabs, `?tab=preview`, the preview rendering the unsaved form live, and closed jobs open it read-only; `features/jobs/job-post-view.tsx` `JobPostView` is the single renderer of a job post for both the preview and `/jobs/:id`, so they cannot drift). `components/require-role.tsx` guards role pages; `features/catalog/catalog-picker.tsx` is the shared autocomplete. Company UI (`features/company`): `/companies` (public directory), `/companies/:id` (public page; owner sees Edit profile, admin sees the verify toggle), `/employer/company` (employer editor with Edit/Preview tabs, immediate logo/cover upload). Hiring (`features/applications`, `pages/employer-hiring.tsx`, `/employer/hiring`, navbar "Hiring"): all applicants across the employer's jobs with status buckets and counts, job / name / minimum-rating filters mirrored to `?status=&job=&q=&rating=` (same local-text-state plus `window.location` merge as `/employer/jobs`). `applicant-card.tsx` `ApplicantCard` is the single card for this page and the per-job `/employer/jobs/:id/applicants`: a "Move to stage" select (`nextStatuses` mirrors the server; Hired and Rejected ask via `ConfirmDialog`), star rating (`rating-stars.tsx`), a `PersonAvatar` photo, structured resume panel, and `applicant-details.tsx` (a Sheet with notes and status history). Stage labels and colours: `STATUS_LABEL`/`STATUS_STYLE` in `applications.api.ts`. `CompanyProfileView` is the single renderer for the public page and the preview; `CompanyLogo`/`CompanyCover` generate an initials logo and gradient when no image is uploaded; job cards and `JobPostView` link to the company (stretched title link with the company link above it, no nested anchors); `components/list-card.tsx` (`ListCard`/`ListRow`) is the shared add-button list. The navbar shows Companies to everyone and Company profile to employers. Query keys `['profile']`, `['jobs']`, `['matching']`, `['applications']` are prefixes that mutations invalidate together. Candidate dashboard (`/dashboard`, `pages/dashboard.tsx`, client only, no endpoint of its own): profile checklist from the pure `features/profile/completeness.ts` (field presence, not the AI review's completeness score), stats from `countMyByStatus`, resume review score, 3 latest applications, 3 recommendations (`useRecommended` only runs once a resume exists, since the server answers 409 without one); `useEvaluation` is mounted only with a saved resume for the same reason. `components/stat.tsx` (`Stat`, also used by the admin overview) and `components/progress-bar.tsx` are shared. Candidates see their own status history: `listCandidateApplications` embeds `history` (explicit `select` of `fromStatus`, `toStatus`, `createdAt`, never notes or rating) and `/applications` shows it in a "Status history" `<details>` under each card; `features/applications/status-history.tsx` `StatusHistory` is the single renderer, shared with the employer `applicant-details.tsx` sheet. Landing page (`/`, `pages/home.tsx` composing `features/landing/sections.tsx`: Hero, HowItWorks, Audiences, LatestOpenings, Transparency, Faq, FinalCta): design from the ui-ux-pro-max Job Board entry (flat, no shadows or gradients, Geist kept). Brand tokens `--brand`, `--brand-foreground`, `--brand-soft`, `--success` live in `index.css` (light and dark) and are used only by the landing and footer; the app theme stays neutral grey, so never repoint `--primary` for the landing. `use-landing-cta.ts` picks role-aware CTAs (guest, candidate, employer, admin); while `status` is `loading` the CTA rows render `invisible` to keep their space, and links only point at pages the viewer's role can open (guests go to `/register`, never to guarded pages). `weights.ts` holds the sample weights shown in `match-card-mock.tsx` and the Transparency bar (they mirror `ENGINE_V1`; update them if a new engine version changes weights); `applicants-mock.tsx` is a static sample, names and numbers are made up and labelled. `LatestOpenings` uses `usePublicJobs` and renders nothing when there are no active jobs. The FAQ uses native `<details>`; its copy states real behaviour (consent, frozen scores, what employers see), so change it when that behaviour changes, and the page makes no pricing claims. `components/site-footer.tsx` (`SiteFooter`, rendered in `App.tsx` on every page) is role-aware like the CTAs. The navbar shows only Jobs and Companies to signed-out visitors. `index.html` has description, Open Graph and `theme-color` meta (no share image yet) and the tab icon `public/favicon.png` (icons8, 96px; the icons8 free licence needs a visible credit link, not added; `public/favicon.svg` is unused).
- `server/` (`@elevateai/server`): Express 5 + TypeScript on Bun, Prisma 7 (`@prisma/adapter-pg`) + PostgreSQL with pgvector, Zod 4, helmet, cors.
  - Feature modules with MVC: `src/modules/<name>/` holds `<name>.routes.ts` (paths + middleware only), `<name>.controller.ts` (HTTP in/out only, no business logic), `<name>.service.ts` (business logic + Prisma, no `req`/`res`) and `<name>.schema.ts` (Zod input schemas) when the module takes input. The Prisma schema is the Model layer; there is no view/serializer layer. Create only the files a module needs. Flow: routes -> controller -> service -> Prisma.
  - `src/index.ts`: startup and graceful shutdown. `src/app.ts`: `createApp()` (helmet, cors, auth handler, json, `/api` router, error handlers). `src/routes.ts`: mounts module routers under `/api`; register new modules here.
  - `src/config/env.ts`: Zod-validated `process.env`; exits on invalid config. Import `env` from here, never read `process.env` elsewhere. `src/config/db.ts`: single `prisma` client plus `connectDb` / `isDbConnected` / `disconnectDb`.
  - `src/middleware/errors.ts`: shared `notFound`, `errorHandler`, `HttpError(status, message)`. Error responses are `{ error: { message } }`; 5xx messages are masked.
  - `modules/auth`: `auth.config.ts` is the Better Auth instance (email/password, Prisma adapter, DB-backed rate limits); `role` is an extra user field, sign-up must send `candidate` or `employer` (enforced in `hooks.before`, for every caller) and `/update-user` cannot change it. `auth.routes.ts` serves `/api/auth/*` and is mounted before `express.json()`; the public entry points are `POST /api/auth/register` and `POST /api/auth/login` (Zod `auth.schema.ts`, `registerUser` / `loginUser` in the service, both set the session cookie; login gives one generic 401 for wrong email or password; 5/min IP limit each via `express-rate-limit` (production only), because Better Auth's limiter skips server-side calls). Google sign-in is on when `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` are both set (client flag `VITE_GOOGLE_AUTH=true`; redirect URI `<BETTER_AUTH_URL>/api/auth/callback/google`): `disableImplicitSignUp` is on, so `/login` only signs in existing users and `/register` sends `requestSignUp` plus the chosen role in `additionalData`; `databaseHooks.user.create.before` sets the role from that OAuth state through the pure `resolveSocialRole` (`auth.role.ts`, only candidate/employer, else candidate) and `create.after` creates the employer Company; account linking is Better Auth's default (verified on both sides); client `features/auth/google-button.tsx` also toasts the `?error=` code on return. Better Auth's raw `/sign-up/email` and `/sign-in/email` are blocked with 404; sign-out and session stay on Better Auth (`POST /api/auth/sign-out`). `auth.routes.ts` also overwrites the `x-client-ip` header with `req.ip` before the Better Auth handler (and `auth.config.ts` reads it via `advanced.ipAddress.ipAddressHeaders`), otherwise Better Auth rate-limits all clients in one shared bucket; when deployed behind a proxy set `TRUST_PROXY` (hop count, see Environment), which `app.ts` passes to Express `trust proxy`. Shared helpers: `middleware/validate.ts` (`validate(schema)` -> 400 with `details`) and `HttpError(status, message, details?)`. `auth.middleware.ts` has `requireAuth` (sets `req.auth`) and `requireRole(...roles)`. `auth.service.ts` has `ensureAdmin`.
  - Matching (design in `IMPLEMENTATION_PLAN.md` section 1a). The score is a pure function: `modules/matching/matching.engine.ts` (`matchEngine`, `checkEligibility`) with weights in `matching.config.ts` (`ENGINE_V1`: skills 35, experience 20, domain 15, education 10, leadership 10, certifications 10; unspecified dimensions are skipped and weights renormalise). No DB, clock, randomness or network in it; arithmetic is integer basis points. V1 was revised once before launch to add education; now that applications store their score and engine version, a change to a weight or rule needs a new engine version, never an edit to V1. Only fields the engine reads affect a score: summary, role company/dates/description and education field/institution/dates are display-only (shown to employers, part of the content hash, never scored). `matching.service.ts` has `scoreMatch` (the one place a profile and a job become a score, used by gap, recommendations and apply), `getGap` (`GET /api/jobs/:id/gap`) and `recommendJobs` (`GET /api/jobs/recommended`). Mount `matchingRouter` before `jobsRouter` in `routes.ts` (its `/jobs/recommended` must beat `/jobs/:id`).
  - `modules/catalog`: curated `CatalogTerm`/`CatalogAlias` (kind `skill|certification|domain`, stable ids like `skill:react`); `GET /api/catalog?kind=&q=`; `seedCatalog` is an idempotent upsert (`bun run db:seed-catalog`; the Playwright server command runs it). `termNamesFor` and `assertApprovedTerms` are the shared helpers; every id stored in a profile or job must be an approved term. `catalog.normalize.ts` makes alias keys (so `React.js` = `reactjs`).
  - `modules/candidate-profile`: `GET/PUT /api/candidate/profile`, `GET /api/candidate/profile/versions`, `POST .../versions/:id/restore` (candidate only). Content is canonicalised and sha256-hashed (`canonicalizeProfile`, `lib/content-hash.ts`); saving identical content reuses a `ProfileVersion`, restore only repoints `currentVersionId`. Roles and education keep the order the candidate arranged (it is what the resume prints), so their order is part of the hash and rearranging them makes a new version with an unchanged score; skills, certifications, other skills, locations and work modes are still sorted and deduplicated. Versions are immutable: never update one in place. Contact details (phone, contact email, city/country, LinkedIn/GitHub/website/other links) are deliberately NOT part of a version: they live in `CandidateProfile.contact` (JSON), are saved by the same `PUT` (as an optional `contact` object; omitting it keeps what is stored), never enter the content hash or the score, and are not touched by restore. Links must be http(s) (`contactSchema`); `parseStoredContact` reads them back and returns empty if stored data no longer validates. Employers see the candidate's current contact in the applicants response only for their own jobs' applicants. Stored content is JSON, so new fields need no migration: read it through `parseStoredProfile` / `parseStoredJob` (they re-apply schema defaults to older versions) instead of casting. The optional resume photo is also outside the versions (never hashed, scored or restored): PNG/JPEG up to 512 KB in `PhotoBlob` (content-addressed, immutable, behind `candidate-photo.ts` only), `CandidateProfile.photoId`; `PUT|DELETE|GET /api/candidate/profile/photo` and `GET .../photo-info` (candidate only). Applying copies `photoId` onto the `Application`, so employers see the photo submitted, via the employer-only `GET /api/employer/applications/:id/photo` (own jobs' applicants, else 404). Client: `PhotoCard` on `/resume`, `PersonAvatar`, and the resume sheet/PDF take a data-URL `photo` in the model.
  - `modules/jobs`: public `GET /api/jobs` (active only; filters `q`, `workMode`, `employmentType`, `domainId`, `companyId`; cursor) and `GET /api/jobs/:id`, both embedding the employer's `company` ref; employer `/api/employer/jobs` CRUD plus `publish|unpublish|close` (draft <-> active, active -> closed; other moves 409). Same immutable-version scheme (`JobVersion`); publishing or editing an active job needs at least one scored requirement. Display-only job fields (never scored, not in `hasScoredRequirement`): `employmentType` (`full_time|part_time|contract|internship`, also a `/jobs` filter), `applicationDeadline` (`YYYY-MM-DD`, shown only, does not auto-close), and the ordered text lists `responsibilities`, `qualifications`, `perks`, `otherDetails` (max 20 items, 300 chars each; `canonicalizeJob` keeps order, drops repeats, and omits empty lists so older hashes stay valid; the form edits them as `{ value }` rows via `ListCard` in `employer-job-form.tsx`).
  - `modules/applications`: `POST /api/jobs/:id/apply` freezes the profile version, job version, score, breakdown and engine version; `GET /api/candidate/applications`; `GET /api/employer/jobs/:id/applicants` (ranked by score); `PATCH /api/applications/:id/status`. Stages are `PIPELINE` in `applications.schema.ts`: applied, under_review, technical_interview, culture_fit, offer, hired, plus rejected. Moves are forward-only (a stage may be skipped), rejected is allowed from any non-final stage, hired and rejected are final (409); every move writes an `ApplicationStatusHistory` row in the same transaction. Company-wide hiring: `GET /api/employer/applications` (filters `status|jobId|q|minRating`, keyset cursor, returns per-status `counts`; shares `applicantInclude`/`presentApplicants` with the per-job list so the two cannot drift), `GET /api/employer/applications/:id/activity` (status history + notes), `POST|DELETE /api/employer/applications/:id/notes` (1-2000 chars), `PATCH /api/employer/applications/:id/rating` (1-5 or null; DB CHECK). Notes and rating are the employer's private opinion: `ApplicationNote` and `Application.rating`, never scored, never returned by a candidate endpoint; all of these check ownership through `job.employerId` (404 otherwise).
  - `modules/company`: one `Company` per employer (created at employer registration, backfilled by the migration, and recreated by `ensureCompany` if missing). Public `GET /api/companies` (directory, `q`/`domainId`, opaque keyset cursor on (verified, name, id) from `company.cursor.ts` so paging survives a verification change; a foreign cursor is a 400), `GET /api/companies/:id` (profile plus that company's active jobs), `GET /api/companies/:id/logo|cover`; employer `GET|PUT /api/employer/company` and `PUT|DELETE /api/employer/company/logo|cover` (raw image body); admin `PATCH /api/admin/companies/:id/verification`. `verified` is admin-only: it is not in `companySaveSchema`, so an employer payload cannot set it, and `saveOwnCompany` clears it when the name, website or links change (`identityChanged`), so a verified company cannot be renamed into someone else. Image requests check the etag with a small query first (`getImageMeta`) and answer 304 without reading the blob. Images (PNG/JPEG/WebP, logo 512 KB, cover 2 MB, type decided from file bytes) are stored in Postgres (`CompanyImage`) behind `company.images.ts` only, so object storage can replace it; image URLs carry the etag (`?v=`) and are cached immutable. Job cards, job pages and recommendations embed `company` (`company.ref.ts`: `companyRefSelect`, `toCompanyRef`). Text content is current information (not versioned, never scored); stored JSON is read back through `readLinks/readLines/readCulture/readAwards`, which return empty on invalid data.
  - `modules/notifications`: in-app inbox (`Notification`, any signed-in role, always scoped to the caller): `GET /api/notifications` (cursor, newest first, returns `unreadCount`), `GET .../unread-count`, `POST .../:id/read` (404 for someone else's), `POST .../read-all`. Entries are written inside the same transaction as the event by `createNotification(tx, ...)`: `changeApplicationStatus` notifies the candidate (link `/applications`), `applyToJob` notifies the employer (link `/employer/hiring?job=<id>`). Status changes also email the candidate: `changeApplicationStatus` sends `applicationStatusMail` (pure, in `mail.templates.ts`, reusing `statusMessage` so the email and the in-app text match) only after the transaction commits, and skips candidates with `User.emailNotifications = false` (default true; set only by `PUT /api/me/email-notifications` `{ enabled }`, returned by `GET /api/me`, not a Better Auth field) and suspended users. Mail is best effort (no queue). Client: `EmailNotificationsCard` on `/account` (candidates). Wording is in pure `notifications.messages.ts` (rejection is worded neutrally); title/body/link are stored text, and links are internal paths only. Users can delete one (`DELETE /api/notifications/:id`, 404 for someone else's or a missing id, since the delete is by id and owner in one query) or clear their whole inbox (`DELETE /api/notifications`). Expiry (`notifications.retention.ts`, pure `retentionCutoffs`): read entries after 30 days, every entry after 90; `pruneNotifications` in the service does it, run by `bun run notifications:prune` (for an external cron) and by a timer in `index.ts` at startup and every 6 hours (per instance, idempotent, errors only logged; move to BullMQ when Redis arrives). The list cursor is a row id, so a delete or prune of that exact row between two page requests ends a scroll early (every delete refetches from the top). Client: `features/notifications` `NotificationBell` in the navbar (per-item delete button, "Clear all" with a `ConfirmDialog` outside the menu) polls the unread count every 30 s and on focus (no sockets yet); the list loads only while the menu is open.
  - `modules/ai` + `modules/resume-import` (AI feature 1, design in `IMPLEMENTATION_PLAN.md` 1c): `ai/ai.provider.ts` `extractObject` is the only place the Vercel AI SDK (`ai`, `@ai-sdk/openai`) is called (`OPENAI_API_KEY` optional, 503 when unset; `AI_MODEL_EXTRACT`, default `gpt-6.1-sol`). `POST /api/candidate/profile/import` (candidate, raw PDF/DOCX up to 5 MB, type decided from bytes in `resume-import.file.ts`, 10/hour per user in production, in-memory) sends a PDF natively or DOCX text (mammoth) to the model and returns `{ content, termNames }` without saving. Pure `mapExtraction` resolves names to approved catalog ids through `CatalogAlias`; misses go to `unmapped`; `leadershipLevel` and preferences are never imported. Client: `features/profile/import-card.tsx` on `/resume` fills the form via `reset(..., { keepDefaultValues: true })` so it shows as unsaved; contact, leadership and preferences are kept. Verified live with `gpt-6.1-sol` (PDF and DOCX, about 10 s). Sol is a reasoning model and rejects `temperature`, so consistency comes from the prompt: it carries today's date (so "Present" roles get real years) and a fixed years-to-level rubric for skills; change those in `systemPrompt()` and re-run a live check.
  - `modules/resume-evaluator` (AI feature 2): `GET|POST /api/candidate/profile/evaluation` (candidate). Reviews the SAVED current version (409 if none): five dimensions 0-100 from the model (rubric and weights in `resume-evaluator.config.ts`, `RUBRIC_V1`; changing a weight or rule needs a new `RUBRIC_VERSION`, never an edit), `overall` computed by the pure `buildEvaluation` (not the model), plus strengths, weaknesses and keyword suggestions. Stored in `ResumeEvaluation`, unique on (user, `contentHash`, rubric version), so the same content is never re-evaluated and costs no quota; 5 new ones per user per day, counted from rows (429). Only resume content is sent (readable labels, never contact, photo, notes or ratings). Advice only: not the match score, never returned by an employer endpoint. Client: `EvaluationCard` in the `/resume` sidebar (button disabled while the form is dirty); `EVALUATION_KEY` sits under `['profile']`, so a save or restore refetches it.
  - `modules/job-assistant` (AI feature 3): `POST /api/employer/jobs/ai-draft` (employer, `{ text }` 20-12000 chars, 20/hour per user in production, in-memory) drafts the job form from a pasted description and saves nothing. Fills only title, description, employment type, the four text lists and catalog skills (`required` flag, resolved by alias with `lookupAliases` in `catalog.service.ts`, which resume import also uses; misses come back as `unmappedSkills`). It never fills a scored or eligibility field (years, domain, degree, leadership, certifications, salary, location, work mode, deadline): `mapJobDraft` is pure and tested for that. Client: `features/jobs/ai-draft-card.tsx` above Basics in `pages/employer-job-form.tsx` (hidden for closed jobs); the result goes in via `reset(..., { keepDefaultValues: true })` so the form shows as unsaved, with a `ConfirmDialog` when the form already has content, and new skills start at level 3 with no years like the manual picker.
  - Gap explanations (AI feature 4, in `modules/matching/gap-explanation.*`): `GET|POST /api/jobs/:id/gap/explanation` (candidate; same 404 for non-active jobs and 409 for no resume as `getGap`, which it calls). The POST writes an AI note on how to close the gap, stored in `GapExplanation` unique on (user, profile version, job version, engine version, `PROMPT_VERSION`), so the same inputs are never explained twice and a stored read costs nothing; 20 new per user per day counted from rows (429). The pure `buildExplainInput` is the only data the model sees: public job requirements, the candidate's skill names/levels/years, certification names, highest degree, leadership label, gap numbers and eligibility labels; never contact, photo, summary, role text or preference values (unit-tested). Advice only: numbers come from `matchEngine`. Bump `PROMPT_VERSION` when the prompt or output shape changes. Client: `features/matching/gap-explanation.tsx` in `MatchPanel` under the breakdown (score < 100), on demand via an "Explain this gap" button; its query sits under `MATCH_KEY`, so profile/job/apply changes refetch it.
  - Applicant summary (AI feature 5, `modules/applications/applicant-summary.*`): a 2-3 sentence neutral description of the frozen resume snapshot, stored on `Application.summary` (+ `summaryModel`, `summaryVersion`), shown only to employers (`presentApplicants` returns it; candidate endpoints use explicit field maps and must never add it). `ensureSummary(applicationId)` never throws and only fills an empty column: it runs fire-and-forget after the `applyToJob` transaction commits (the model can never slow or fail an apply) and lazily for up to 3 rows with a null summary on each employer list request (covers failures and old applications); in-memory in-flight set, to be replaced by a queue when BullMQ/Redis arrive. `buildSummaryInput` (pure, tested) is all the model sees: skills, role titles/years/industry/description, degree level and field, certifications, leadership, with emails, links and phone numbers scrubbed; never the name, contact, photo, company or school names, dates, or preferences. The prompt forbids recommendations and any mention of protected traits or career gaps; `cleanSummary` post-scrubs and caps the output. `AI_ENABLED=false` makes `extractObject` answer 503 for every AI feature. `AI_STUB=true` (test-only, refused when `NODE_ENV=production`, warns at startup) makes `extractObject` return the caller's canned `stub` output through the real schema (`modules/ai/ai.stub.ts` `resolveStub`) instead of calling OpenAI; every `extractObject` caller must pass a `stub`. The default e2e stack uses the stub so tests never reach OpenAI (the apply flow would otherwise call the model in every test). Client: `ApplicantCard` shows it under the header; `useApplicants`/`useEmployerApplications` poll every 5 s (at most 12 updates) while any row lacks one.
  - AI consent (`modules/ai/ai-consent.ts`): `User.aiConsentAt` + `aiConsentVersion` (not in Better Auth `additionalFields`, so `/update-user` cannot set them). `POST|DELETE /api/me/ai-consent` (any signed-in role) record or withdraw agreement to send text to OpenAI; `GET /api/me` returns `aiConsent` (true only for the current `AI_CONSENT_VERSION`; bump it when the notice changes so users agree again). `requireAiConsent` (403 with `details: [{ field: 'aiConsent' }]`) sits right after `requireRole` on every route that calls the model: resume import, resume evaluation POST, job assistant, gap explanation POST; GETs that only read stored results are open. `ensureSummary` also returns quietly unless the application's candidate has current consent (the lazy path retries if they agree later). Withdrawal stops new AI calls; results already stored are kept (the `/privacy` page says so). Client: `features/auth/use-ai-consent.tsx` `useAiConsent()` returns `withAiConsent(action)` (shows a `ConfirmDialog` the first time, records consent, then runs the action), `retryOnConsentError(err, retry)` for a stale client state and `consentDialog` (render it in the card); used by the import, evaluation, job-draft and gap-explanation cards. `/privacy` (`pages/privacy.tsx`, copy needs legal review and the operator contact line), a footer link in `App.tsx`, and an AI features card with Withdraw on `/account`. E2E users that call AI routes must be given consent first.
  - `modules/admin` (moderation, client `/admin` dashboard with Overview/Users/Jobs/Companies tabs in `pages/admin.tsx`, `features/admin`): admin only. `GET /api/admin/overview|users|jobs` (filters `q`, `role`/`status`, `suspended`, id cursor), `POST|DELETE /api/admin/users/:id/suspension` and `.../jobs/:id/suspension` (POST needs `{ reason }` 3-500 chars). Suspension is `suspendedAt` + `suspendedReason` on `User` and `Job`, separate from `JobStatus` so publish/unpublish cannot clear it; data is never deleted. A suspended user: `requireAuth` answers 403 `Account suspended`, `databaseHooks.session.create.before` in `auth.config.ts` blocks every other way of getting a session (login maps it to the same 403), suspending deletes their sessions in the same transaction, and `suspendedAt` is `input:false` and blocked on `/update-user`. Admins cannot be suspended, nor suspend themselves. Public job list/page, recommendations, gap, apply, and the company directory/page/logo/cover (`getPublicImageMeta`) all filter out suspended jobs and jobs/companies of suspended employers (add the same `suspendedAt: null` + `employer: { suspendedAt: null }` to any new public job query). A suspended job stays visible to its employer with the reason; edit/publish/unpublish answer 409, close is still allowed. Suspending or restoring a job writes a `moderation` notification (`moderationMessage`) to the employer. Company verification stays in the company module (`PATCH /api/admin/companies/:id/verification`); the Companies tab reuses it. Client: a 403 `Account suspended` from any call clears the user (`lib/api.ts` interceptor, `useSession`). Audit log: `AdminAuditLog` (no foreign keys, so deleting a user or admin keeps the trail; actor email and target label are text snapshots), written by `recordAudit(tx, adminId, ...)` (`admin.audit.ts`) inside the same transaction as user suspend/restore, job suspend/restore, company verify/unverify (the admin id is threaded through those services); `GET /api/admin/audit` (filters `action`, `q`, id cursor), client Audit tab. Delete user: `DELETE /api/admin/users/:id` with `{ confirmEmail }` matching the user's email (400 otherwise; 409 for self or admins), a hard delete that relies on the `onDelete: Cascade` on every User relation (an employer's delete also removes other candidates' applications to their jobs); unused `PhotoBlob`s are removed afterwards with `deleteIfUnused`. Client `DeleteUserDialog` asks to type the email.
  - `modules/user`: `GET /api/me`. `modules/health`: `GET /api/health`. `modules/home`: `GET /` at the server root (outside `/api`, mounted in `app.ts`).

  - Prisma client is generated to `server/generated/prisma` (gitignored); import from `../../generated/prisma/client` (see `src/config/db.ts`).
- `docker-compose.yml`: `pgvector/pgvector:pg17` on host port **5433** (user/password/db: `postgres`/`postgres`/`elevateai`).

```
bun install

cd server && bun run db:migrate  # prisma migrate dev
cd server && bun run db:deploy   # prisma migrate deploy

cd server && bun run db:seed-catalog # seed skills/certifications/domains (idempotent)
```

Playwright (e2e) is set up in `playwright.config.ts` with specs in `e2e/` (home, auth, catalog, profile, contact, education, resume, jobs, employer-jobs, matching, applications, company, hiring-api, hiring-ui, candidate-photo-api, candidate-photo-ui, notifications-api, notifications-ui, ai-import, ai-evaluator, ai-job-assistant, ai-gap-explanation, ai-applicant-summary, ai-consent; the default stack runs with `AI_STUB=true` (every `extractObject` call returns the feature's canned `STUB` output, deterministic, never OpenAI; put `__stub_fail__` in model-bound text to force a 502; see `support/ai.ts` for `tinyPdf`/`tinyDocx`/`importResumeApi`) and the verification stack keeps `AI_ENABLED=false` (503); the AI routes sit behind `requireAiConsent`, so a spec that needs to get past the gate calls `grantAiConsent(request)` from `support/auth.ts` first; the `ai-*-success` specs cover the success paths against the stub, the other `ai-*` specs cover guards and validation; helpers in `e2e/support/`, e.g. `support/company.ts` has the employer/candidate/admin fixtures and image fixtures). The e2e server command also seeds the catalog. It runs against a separate database `elevateai_test` (same Docker container; override with `TEST_DATABASE_URL`, see `server/.env.test.example`) on its own ports: server 4100, client 5174 (the Vite proxy target comes from `API_PROXY_TARGET`). `server/scripts/test-db.ts` refuses any database not named `*_test`; `reset` also removes the seeded e2e admin (`admin@e2e.test`), which the server re-seeds on its next start. Workers are 1 (shared DB). Specs `auth-(verification|password-reset|change-email)*` run in the separate `verification` Playwright project: a second stack (server 4101, client 5175, database `elevateai_verify_test`, `REQUIRE_EMAIL_VERIFICATION=true`) whose `SMTP_URL` points at a local SMTP sink (`e2e/support/mail-sink.ts`, helpers in `support/mail.ts` and `support/verification.ts`); the default stack has verification off and its `SMTP_URL` is pinned to the same sink so tests never send real mail. `test:db:reset` does not reset the verify database (specs use unique emails). Rate limiting (Better Auth and the 5/min `express-rate-limit` on `/register` and `/login`) is enforced only when `NODE_ENV=production` (`env.NODE_ENV`, default `development`), so dev and e2e are unthrottled.

Writing e2e tests: do NOT write, update or run e2e tests on your own, even when a feature or page is added or changed. The user asks for them when a feature is complete. When asked, delegate to the `e2e-test-writer` agent (`.claude/agents/e2e-test-writer.md`) instead of writing specs inline. If the user says to write or run them yourself to save tokens, do it directly in the terminal under the same rules (isolated test stack, never the dev servers). Spec gotchas: a Radix dropdown hides the rest of the page from the accessibility tree while open, so close it (Escape) before asserting on navbar controls; TanStack Query refetches on focus from a `visibilitychange` event dispatched on `window`, not `document`. Give the agent the feature/flow and the behaviours to cover (including failure cases); it reads the code, writes specs and helpers in `e2e/` (shared helpers in `e2e/support/`), runs them against the isolated test stack and reports results. Do not run e2e tests against the dev servers or database. When a change breaks an existing spec (for example a new confirmation modal), the agent updates that spec too; the full suite is run once at the end (`bun run test:e2e`, then `bun run test:db:reset`).

## Environment

Copy `server/.env.example` to `server/.env`. Required: `DATABASE_URL` (matches the docker-compose port 5433), `BETTER_AUTH_SECRET` (min 32 chars). Optional: `ADMIN_EMAIL`, `ADMIN_PASSWORD` (min 12 chars); when both are set the server seeds the admin on startup (idempotent). `NODE_ENV` (`development` default; rate limiting and secure cookies only apply in `production`, so set it in deploys). `TRUST_PROXY` (default 0): number of reverse proxies in front of the API, passed to Express `trust proxy`; set it in deploys or every client shares one rate-limit bucket (never `true`). `OPENAI_API_KEY` (optional; AI routes answer 503 without it, and an empty value fails env validation, so omit the line instead of leaving it blank) and `AI_MODEL_EXTRACT` (default `gpt-6.1-sol`). Defaults: `PORT=4000`, `CLIENT_ORIGIN=http://localhost:5173`, `BETTER_AUTH_URL=http://localhost:4000`. Never commit real secrets; `.env*` is gitignored except `.env.example`.

## Conventions

- Server is ESM TypeScript run directly by Bun; no build step. Imports are extensionless relative paths.
- Client: hard-to-undo actions (applying, closing a job) ask first with `components/confirm-dialog.tsx` (`ConfirmDialog`, shadcn AlertDialog); never use `window.confirm`.
- Style: no semicolons, single quotes, 2-space indent, trailing commas.
- Validate all external input with Zod (schemas in `<name>.schema.ts`); throw `HttpError` for expected failures.
- Migrations: the first one enables pgvector (`CREATE EXTENSION IF NOT EXISTS vector`). Vector indexes (HNSW, cosine) go in hand-edited migration SQL.
- Auth: Better Auth with roles `candidate | employer | admin`; guard routes with `requireAuth` / `requireRole`. Email verification, password reset and change-email use Better Auth's own endpoints (pass-through in `auth.routes.ts`, no Zod or express-rate-limit; only Better Auth `customRules`) and `modules/auth/mail.service.ts` (`sendMail`, fire-and-forget, nodemailer via `SMTP_URL`, console fallback; Mailpit in docker-compose) with HTML + text bodies from pure `mail.templates.ts` (escaped). `REQUIRE_EMAIL_VERIFICATION` (default true) makes login return 403 until verified (Better Auth re-sends the mail) and register return `verificationRequired` with no cookie. With it on, a duplicate sign-up returns the same synthetic response (no enumeration) and `onExistingUserSignUp` mails the owner; `registerUser` skips the employer company for it. With it off, duplicates are 409. Change-email (`user.changeEmail`): approval link to the current address, then a verification link to the new one. Both links, and the verify link, land on client `/verify-email` (`?change=1` for change-email; the page decides "Change approved" vs "Email changed" by comparing `/me` with the address `/account` stored in localStorage). Client pages: `/forgot-password`, `/reset-password`, `/verify-email`, `/account` (change email); resend buttons (login 403 notice, register) use `useCooldown` (60 s, client-only; the server limit is production-only). `getApiError` reads both our `{ error: { message } }` and Better Auth's top-level `{ message }`. Any other URL renders `pages/not-found.tsx` (catch-all route); the server's `notFound` answers JSON 404.
- Deploy: one origin, because the client calls relative `/api` and the session cookie needs it. `docker-compose.prod.yml` (project `elevateai-prod`, separate from dev) runs `web` (Caddy from `Dockerfile.web`, config `deploy/Caddyfile`: serves `client/dist` with SPA fallback, proxies `/api/*`), `server` (`server/Dockerfile`, build context is the repo root), `db`, `redis`; it sets `TRUST_PROXY=1` (Caddy is one hop) and needs `POSTGRES_PASSWORD` in the shell. Copy `server/.env.production.example` to `server/.env.production` (the checklist is in it). Migrate and seed with `docker compose -f docker-compose.prod.yml run --rm server bun run db:deploy` and `... db:seed-catalog`. Verified locally at `https://localhost`: `__Secure-` cookie, 6th bad login answers 429, SPA deep links work. Not covered: image registry/CI build, backups, Redis auth, managed hosts.
- Planned stack (not yet built): BullMQ + Redis workers, Socket.IO, Vercel AI SDK for LLM calls. Keep to these when implementing those phases.
